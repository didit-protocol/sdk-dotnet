# Contributing to the Didit .NET SDK

This repository is one of the seven official Didit server SDKs (`sdk-python`, `sdk-node`, `sdk-go`, `sdk-java`, `sdk-php`, `sdk-ruby`, `sdk-dotnet`).
[docs/DESIGN.md](docs/DESIGN.md) is their shared contract and it is binding: when the code and the design disagree, the code is wrong.

## Toolchain

- .NET SDK 10, plus the .NET 8 and .NET 9 runtimes (installing the 8.0, 9.0 and 10.0 SDKs is simplest). The library targets `net8.0` and `netstandard2.0`; the tests run on `net8.0`, `net9.0` and `net10.0`, and also on `net472` when built on Windows, which exercises the `netstandard2.0` build on .NET Framework. `global.json` requires SDK 8.0.100 or later and rolls forward to the newest installed major.
- Python 3.10 or later for the generator. Standard library only; there is nothing to install.
- Nullable reference types are enabled, warnings are errors and the .NET analyzers run in the build, so the build is the static check.

## Core and generated code

The SDK has two layers, kept strictly apart (DESIGN.md section 5).

- **Core** (hand-written, small, fully tested): `src/Didit/` outside `Generated/`, that is configuration, HTTP transport, authentication headers, retries, timeouts, errors, pagination, `Optional<T>`, multipart and binary bodies, webhook verification and the Authentication helpers, plus `src/Didit.Extensions.DependencyInjection/`.
- **Generated**: `src/Didit/Generated/` and `tests/Didit.Tests/Generated/`, produced by `codegen/` from `openapi/`. Every generated file starts with `Code generated by codegen from openapi/*.json. DO NOT EDIT.` Never edit it by hand: change the generator in `codegen/` or the naming in `openapi/overlay.json`, then regenerate. CI fails when the committed generated code is stale.

The files in `openapi/`:

| File | Owner |
|---|---|
| `verification.json`, `account.json` | Upstream copies from docs.didit.me, updated only by the spec sync. Never edit by hand. |
| `webhook-vectors.json` | Upstream copy of the backend's webhook signing vectors. Never edit by hand. |
| `SOURCE.json` | URL, SHA-256 and fetch time of each upstream file, written by the spec sync. |
| `overlay.json` | SDK naming for operations whose upstream definition has no `x-didit-sdk` yet. Edited in this repository. |
| `deprecated-operations.json` | Present only while removed or renamed operations are deprecated; written by the spec sync. |

## Regenerating

```sh
python3 codegen/generate.py                      # rewrite src/Didit/Generated and tests/Didit.Tests/Generated
python3 codegen/generate.py --check              # exit 1 when the committed generated code is stale
python3 -m unittest discover -s codegen/tests    # generator and spec sync unit tests
```

Commit the regenerated files together with the change that caused them.

## Adding SDK naming for a new operation

Every operation needs SDK naming (DESIGN.md section 4).
When upstream adds an operation without `x-didit-sdk`, `python3 codegen/generate.py` fails and names the operation and its `operationId`.
Add an entry under `"operations"` in `openapi/overlay.json`:

```json
"POST /v3/organization/{organization_id}/application/{application_id}/cases/teams/": {
 "auth": "api_key",
 "method": "create",
 "resource": "cases.teams",
 "scope": "application",
 "server": true
}
```

- Key: `"<METHOD> <path>"` for `verification.json`, `"account <METHOD> <path>"` for `account.json`, with the path exactly as in the spec.
- `resource`: dot path of snake_case resource names; each segment becomes a nested accessor (`client.Cases.Teams`).
- `method`: snake_case method name; `create` becomes `CreateAsync`.
- `auth`: `api_key`, `account_token`, `none`, `device_token` or `public`.
- `server`: `false` for operations that use an end-user or device token; server SDKs do not expose them.
- `scope`: `"application"` exactly when the path starts with `/v3/organization/{organization_id}/application/{application_id}/`; omit it otherwise.

Keep the keys sorted and the file's 1-space indentation.
Follow the naming of neighbouring operations, add the same entry to `overlay.json` in the other six SDK repositories, then regenerate, build and test.
Better still, get `x-didit-sdk` into the upstream OpenAPI document in mintlify-docs: once upstream carries it, the spec sync deletes the overlay entry.

## Build, test and format

```sh
dotnet build Didit.sln -c Release
dotnet test tests/Didit.Tests/Didit.Tests.csproj -c Release -f net8.0
dotnet format Didit.sln --verify-no-changes --exclude src/Didit/Generated tests/Didit.Tests/Generated
dotnet pack src/Didit/Didit.csproj -c Release -o artifacts
dotnet pack src/Didit.Extensions.DependencyInjection/Didit.Extensions.DependencyInjection.csproj -c Release -o artifacts
```

Use `-f net9.0`, `-f net10.0` or, on Windows, `-f net472` for the other target frameworks.
Unit tests never touch the network; HTTP is mocked.

### Smoke tests

`tests/Didit.SmokeTests` runs against a live sandbox application and is skipped unless `DIDIT_SANDBOX_API_KEY` is set:

```sh
DIDIT_SANDBOX_API_KEY=<sandbox key> dotnet test tests/Didit.SmokeTests/Didit.SmokeTests.csproj -c Release
```

Use a sandbox key only, never a live one, and never commit it.
Smoke tests do not run in default CI and create nothing that costs money beyond sandbox sessions.

## Spec sync

`.github/workflows/spec-sync.yml` runs daily and on demand (DESIGN.md section 3.1).
`codegen/spec_sync.py` downloads the upstream documents; when they changed, the workflow regenerates the SDK, builds it, runs the tests on `net8.0` and opens or updates the pull request `chore(spec): sync API spec YYYY-MM-DD` on branch `chore/spec-sync`.
Its body lists added, removed and changed operations and schemas, the breaking changes, and the result of each step.

- **`needs-naming` label**: a new operation has no SDK naming. Add the overlay entry (above), regenerate, and push to `chore/spec-sync`. The sync does not overwrite that branch while it has commits from people.
- **Removed operations** are never deleted silently. The spec sync copies them, with the schemas they reference, into `openapi/deprecated-operations.json`; the generator keeps their SDK methods, marked `[Obsolete]`, until the next minor release. Delete the entries in that release.
- **Renamed operations** (upstream `x-didit-sdk` with a new resource or method) keep their old method as an `[Obsolete]` alias of the same endpoint until the next minor release: the spec sync records the old name in `openapi/deprecated-operations.json` (key suffix ` (renamed from <resource>.<method>)`). Delete the entry in that release.
- **Moved endpoints**: when an operation's path changes, give the new path the old naming (upstream or in `overlay.json`). The method keeps its name and calls the new path; a deprecated copy of the old path with the same name is ignored by the generator, and the spec sync reports the pair under "Moved" instead of deprecating it.
- **Release impact**: `chore` commits do not trigger a release. When a sync adds or changes public SDK surface, set the squash commit title to `feat(spec): sync API spec YYYY-MM-DD` (or `fix(spec):`, with `!` when it is breaking) when merging.

Preview a sync locally without writing anything with `python3 codegen/spec_sync.py`.

## Commits and releases

- Commit messages and pull request titles follow [Conventional Commits](https://www.conventionalcommits.org/). The type must match the semver impact: `feat` for new public API, `fix` for bug fixes, `perf`, `deps`, `docs`; `!` or a `BREAKING CHANGE:` footer for breaking changes. While the version is `0.x`, a breaking change bumps the minor version and a feature bumps the patch version.
- [release-please](https://github.com/googleapis/release-please) keeps a release pull request open on `main`. Merging it updates `CHANGELOG.md`, `.release-please-manifest.json` and the version in `Directory.Build.props`, tags `vX.Y.Z` and creates a draft GitHub release.
- `CHANGELOG.md` is generated from the commits. Never edit it by hand.
- Publishing the draft release runs `.github/workflows/release.yml`: it checks that the tag matches the version, builds, tests, packs, and then waits for approval in the `nuget` environment before it pushes `Didit` and `Didit.Extensions.DependencyInjection` (with symbols) to nuget.org through trusted publishing and attaches the packages to the release.
- Never publish a package, push a release tag or make this repository public without Alex's explicit approval. Nothing is released before the 2026-11-01 Didit release.

## Keeping the seven SDKs in sync

- Any public API change in `service-didit-verification` or `service-didit-auth` must reach the OpenAPI documents in mintlify-docs, and from there every server SDK through the spec sync pull request.
- A change to hand-written core behaviour that DESIGN.md describes (client options, errors, retries, pagination, webhooks, Authentication) is made in all seven SDK repositories, one pull request each, and DESIGN.md is updated in all seven in the same words.
- A capability shipped in one server SDK ships in the other six.

## Pull requests

- Fill in the pull request template, including the parity line.
- Public API changes need tests, README updates and a conventional commit type that matches their semver impact.
- Never commit secrets, API keys or real customer data; fixtures are synthetic.

Report security issues privately as described in [SECURITY.md](SECURITY.md).
